# Specification: operationalize-rpm-as-an-extraction-variable

## Problem Statement

The DF64V is a variable-speed grinder, so RPM is a genuinely new extraction variable. RPM is already documented (025: `knowledge/grinders/DF64V.md` quick-tier + `knowledge/reference/DF64V_REFERENCE.md` deep-tier) and 026 added an `RPM` column to the live `grind-map.md`, but no skill recommends, logs, or reasons about it. This feature wires RPM through the dialing workflows (`/new-coffee`, `/feedback`, `/diagnose`, `/consult`) plus a thin knowledge-synthesis layer, all gated to variable-speed grinders and hedged per 025's contested-science findings — so the intermediate home barista gets correct, non-overclaimed RPM handling and a longitudinal RPM log that becomes the real signal over time.

**Architecture decision (post-critical-review):** RPM is **set-and-forget grinder config** — the user runs one operating RPM across many coffees, re-dialing *grind* per bean. So the **current operating RPM lives in `user-setup.md`** (grinder config home), and the **grind-map `RPM` column is a per-shot historical stamp** (the longitudinal record). This corrects the original grain mismatch (026 stored a cross-coffee value in a per-coffee log) and lets skills learn the current RPM from a single `user-setup.md` read they already perform — **no grind-map history parser is needed**, the column populates reliably, and "current RPM" is known even on the first shot of a new coffee.

## Phases

- **Phase 1: Knowledge & data foundation** — author the skill-consumable RPM knowledge + logging rules, add the current-RPM home to `user-setup`, and bring the data templates into sync, so skills cite a single, consistent source of truth.
- **Phase 2: Skill operationalization** — wire the four skills to gate on the variable-speed signal, read the current RPM, stamp it, and consume the Phase-1 knowledge layer — verified by discriminating greps plus an agent-administered fixture trace.

## Edge Cases

- **Fixed-speed grinder (Sette) active**: no RPM prompts; `/feedback` writes a blank RPM cell; `/new-coffee` omits the RPM row; `Operating RPM` unused; `/diagnose` unchanged.
- **Variable-speed grinder, Operating RPM not yet set**: `/new-coffee` recommends the `DF64V.md` reference default; `/feedback` prompts once (light) and writes blank if still unknown — never infers.
- **RPM changed mid-bag**: user states a new RPM ≠ `user-setup` Operating RPM → `/feedback` warns + re-anchors grind AND updates `user-setup` Operating RPM (R11).
- **Grinder unconfigured / `user-setup.md` unreadable / no map match**: Active Grinder contract fallback → RPM behavior OFF, never error.
- **Pre-existing pre-fix grind-map row (the "zero rows" assumption fails)**: the "live file has zero data rows post-026" is a current snapshot, not an invariant. The implementation must, before relying on it, check the live `grind-map.md` for any data row whose column count ≠ 13; if found, flag it to the user rather than silently leaving a column-shifted row. (No automatic back-fill — flag only.)
- **Stale RPM in `/diagnose` context after a grinder switch**: a known RPM is used as advisory context for the shot being diagnosed; if no RPM is known for that shot, `/diagnose` is unchanged. `/diagnose` does not assert RPM facts beyond the routed `DF64V.md` framing.
- **Markdown parse caveat (informational)**: a 13-col row with a blank RPM cell is not structurally identical to a 12-col row with no RPM column for a positional `|`-split parser. Not triggered here (no positional grind-map parser is built — current RPM comes from `user-setup`).

## Technical Constraints

- **Skill files are at `.claude/skills/`** (canonical) — there is **NO `plugins/cortex-core/` mirror and no pre-commit regeneration in this repo**; the CLAUDE.md "edit canonical, mirrors regenerate" line is inapplicable here. Edit `.claude/skills/` directly. Skill edits are lifecycle-protected → implementation runs through `/cortex-core:lifecycle` (this overnight run).
- **RPM gating rides the existing Active Grinder contract (027)** — restate the operative read inline (canonical sentence); gate on the **quick-tier** file's literal `## Motor Speed (RPM)` heading; do not modify the contract.
- **Current RPM lives in `user-setup.md` (R6); grind-map RPM column is a per-shot stamp (026-owned structure); RPM science/numbers are authoritative in the grinder reference files (025).** Skills route to these; they never hardcode RPM numbers (CLAUDE.md guard: RPM is a grinder control, not a temp/pressure claim).
- **All RPM-as-lever guidance inherits 025's seven-fact hedges** — no unqualified "RPM = body"; present as contested/vendor-framed/own-data.
- **Auto-commit**: `/feedback`'s RPM grind-map write and any `Operating RPM` update to `user-setup.md` ride the existing `.data-repo-path` private-repo commit path — no new commit surface.
- **Headless verification protocol (replaces the impossible "interactive dry-run").** Prompt-only skill correctness cannot be fully proven by greps. Each behavioral requirement is verified by **two** headless means an overnight agent can perform with no user: (1) **discriminating structural greps** — presence of *correctly-scoped* wiring (gate clause co-occurring with the RPM instruction in the same block; literal `## Motor Speed (RPM)` heading match) and *absence* of forbidden literals/claims (the broadened R1 body-claim regex; the R15 number regex; the R12 hierarchy-block RPM=0 scan); and (2) an **agent-administered fixture trace** — the verifying agent creates two fixture `user-setup.md` variants (one DF64V variable-speed with an `Operating RPM`; one Sette fixed-speed), then for each skill traces the instructions against each fixture and records the resulting behavior (RPM present/ON for DF64V, absent/OFF for Sette; mid-bag warning fires only on an RPM delta; routine "too sour" yields no RPM). The trace is the agent reasoning through the skill prompt against fixed inputs and recording the outcome — no human interaction required. A requirement passes only when both its grep ACs and its fixture-trace expectation hold.
