# Plan: operationalize-rpm-as-an-extraction-variable

## Overview
Wire RPM through the four dialing skills (`/new-coffee`, `/feedback`, `/diagnose`, `/consult`) plus a thin knowledge-synthesis layer, all gated to variable-speed grinders via the literal `## Motor Speed (RPM)` heading and hedged per 025's contested-science findings. Build the knowledge/data **foundation layer** first (single sources of truth: the DF64V quick-tier "dial-in lever" note, `_NOTATION.md` logging rules, the `Operating RPM` home in `user-setup`, and the synced data templates), then wire the **skill layer** to read those sources at runtime — never hardcoding RPM numbers.
**Architectural Pattern**: layered
<!-- The skill layer (Phase 2) consumes the knowledge/data foundation layer (Phase 1) by reference; the dependency is strictly one-directional, which is why Phase 1 lands first. -->

**Verification engine constraint (read before authoring any AC or running any verification):** the runtime `grep` in this environment is a shell function that routes to **`ugrep 7.5.0`** (basic-regex `-G` mode). It **rejects complex quantified-alternation regexes** with `exceeds complexity limits` (exit 2) — a regex that errors prints no lines, which a naive pass/fail check misreads as "clean = PASS." Every grep AC in this plan is therefore restricted to **fixed strings and simple `\|` alternations** that run under ugrep. **Semantic properties that no grep can decide** — whether a sentence is *hedged*, whether a gate *branches correctly* — are verified by an explicitly-labeled **agent-reasoned audit** (type (c)), never dressed up as a mechanical regex gate. Do not reintroduce `grep -inE "(higher|more|…).{0,40}(…)…"`-style regexes.

**Checkpoint**: all four skills route/gate correctly; the described-input trace shows RPM behavior ON for the DF64V state and OFF for the Sette state across every skill; the global R15 number-literal scan returns 0.
