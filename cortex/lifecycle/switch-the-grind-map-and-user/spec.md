# Specification: switch-the-grind-map-and-user

## Problem Statement

The active data layer still describes the retired Baratza Sette 270: `user-setup.md`'s Grinder field names the Sette (so every grinder-aware skill resolves the wrong grinder), and the live `grind-map.md` records grind settings in Sette macro+micro codes (`13D`, `13E`) that cannot accept DF64V stepless settings without blending two incompatible notations. This item (epic-024 work-streams C/D/G) flips the private-repo data layer to the DF64V + SSP Cast Lab Sweet V3: it archives the Sette grind map as a history-preserving rename, stands up a fresh grinder-agnostic DF64V map (grinder-neutral Grind column + a dedicated RPM column), and repoints the Grinder field — so the selector and the grind-logging destination both reflect the real equipment. The benefit is correct grinder resolution and a clean, notation-consistent logging surface for the DF64V dial-in; the home barista (sole user) is the beneficiary.

## Phases

- **Phase 1: Archive + fresh map** — archive the Sette grind map history-preservingly and create the fresh grinder-agnostic DF64V `grind-map.md` at the same path, staged and committed as ONE atomic commit (with a best-effort, non-blocking telemetry capture).
- **Phase 2: Repoint user-setup** — change the `user-setup.md` Grinder field to the DF64V + SSP V3 (with its RPM note), leaving all other sections untouched.

## Edge Cases

- **Device unreachable / shots already purged:** best-effort telemetry capture skips without blocking or retry-looping; `ratings.json` (contents verified per R1) + the archived map's git history remain the retained record.
- **Working-tree clobber window (pre-commit):** prevented by the mandatory operation ordering in R2 — `git mv` runs **first** (capturing the original under the archive name and vacating the path), and only then is the fresh `grind-map.md` written as a clean create. There is no point at which `grind-map.md` is overwritten while it still holds the sole copy of the Sette history.
- **Crash/abort between the `git mv` and the fresh-file write:** the original Sette content is already safe under `grind-map-sette-270.archive.md` (the `git mv` ran first); re-running creates the fresh file. If a crash happens *before* the `git mv`, nothing was written, so nothing is lost.
- **`git push` fails mid-migration:** the single atomic Phase-1 commit (R4) guarantees no half-migrated *committed* state lacks `grind-map.md`; surface the standard auto-commit failure message and **halt** (R7). The change is recoverable locally; the operator completes the push for off-machine durability.
- **Lineage-severing rename mechanic:** if the archive were created via `cp`+`rm` or a plain filesystem rename instead of `git mv`, R2's `--follow ≥ 12` check fails (and the content-hash check still passes), so the wrong mechanic is caught at acceptance rather than silently severing the audit trail.
- **Fresh empty map vs the Unconfigured-check:** the fresh map ships with its preamble + footer notes (R3(d)), and `user-setup.md` stays fully populated, so the setup does not read as an unconfigured template.
- **025 finalizes a conflicting notation:** low risk — 026 is `blocked-by: 025`, so 025 runs first and 026 consumes its finalized "chirp + N marks" contract (`knowledge/grinders/_NOTATION.md` per 025 research). If 025's final notation differs, the fresh map's `Grind` column and the `user-setup.md` RPM-note string are re-keyed by 025 / a follow-up — the fresh map ships with **zero data rows**, so only the column legend (not historical values) would need re-keying.
- **Transitional 027 window:** until 027 lands, `/feedback` (hardcoded to a 12-field Sette-format row, `feedback/SKILL.md:136`) may write a malformed row into the fresh 13-column map; **accepted** with no special handling (operator expects 027 to follow shortly).
- **Archive rows fill only 11 of 12 cells (blank `Puck Screen?`):** the archive is moved byte-identical — do not "complete" or normalize columns (would break `--follow` and is out of scope).

## Technical Constraints

- All active-data writes occur inside the private data repo (`/Users/charlie.hall/Workspaces/gaggimate-barista-data`) via the symlink targets; commits use `git --git-dir=…-data/.git --work-tree=…-data`, in **separate Bash calls, no `&&` chaining, no `git -C`** (CLAUDE.md auto-commit policy). `.data-repo-path` is present, so auto-commit applies. The Phase-1 archive+fresh-map is a **single** data-writing step → one commit, one push (reconciles atomicity with the per-step policy).
- **Operation ordering (load-bearing):** capture pre-migration hash → `git mv` to archive → write fresh `grind-map.md` → stage both → single commit → push. The destructive `git mv` precedes any write to the `grind-map.md` path.
- The archive must be moved **byte-identical**; renaming + substantially rewriting in the same commit risks dropping below git's ~50% rename-similarity threshold and breaking `git log --follow`/`blame` continuity (the existing 12-commit lineage must survive). Verified position-independently via the pre-captured `hash-object`.
- The fresh map must keep the filename `grind-map.md` — `bin/setup-data-repo.sh:62-64` hard-requires a file of that exact name in the private repo.
- **025 boundary (no inversion):** per 025's research (`build-the-grinder-agnostic-knowledge-layer/research.md:22,53,70`), 025 owns the grinder-neutral notation contract (`knowledge/grinders/_NOTATION.md`, "chirp + N marks") and the `grind-map.example.md` Grind-column legend; **026 owns the live map + the dedicated RPM column by that explicit, agreed division** (not a contract 025 must retro-fit). 026 is `blocked-by: 025`, so it executes **after** 025 and consumes the finalized notation; the free-text "chirp + N marks" Grind column is the minimal fallback only if 025 somehow has not landed. "chirp + N marks" is the notation 025's research converges on (its lines 46/77/81), so the string hard-coded in R3/R6 is consistent with 025.
- MCP stores `grind_setting` as a free-text string with no schema validation, so the stepless notation requires no code change.
- Internal execution order: (best-effort telemetry capture +) archive → fresh map → repoint user-setup.
