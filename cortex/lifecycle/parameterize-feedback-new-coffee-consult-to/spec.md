# Specification: parameterize-feedback-new-coffee-consult-to

## Problem Statement

Three skills hardcode the Baratza Sette 270: `feedback` records grind in Sette macro+micro notation (`9D`) and loads `SETTE_270.md` on grind questions, `new-coffee` falls back to the Sette reference (and Sette codes in its own reference files) when no grind-map match exists, and `consult` routes grinder questions to the Sette document and its deep reference. On the incoming DF64V (epic 024), the agent therefore records settings in a dead notation and offers grinder advice for the wrong machine. This feature makes the three skills read the active grinder from the `user-setup.md` Grinder field and defer to whatever per-grinder reference and shared notation apply — falling back to grinder-relative step advice when no specific reference matches — so the skills behave correctly for the DF64V today and for any future grinder a forker adds, without changing skill logic. It benefits the repo owner now (correct DF64V behavior) and anyone forking the repo for a different grinder.

## Phases
- **Phase 1: Active Grinder field parsing contract** — Verify the 025 dependency landed, then add the single-source-of-truth selection contract to `CLAUDE.md` (read the Grinder field → resolve a per-grinder reference via an explicit keyword→file map → fallback), mirroring the existing Puck Screen parsing contract.
- **Phase 2: Parameterize feedback & consult** — Replace the hardcoded Sette loads/notation in `feedback` and `consult` with contract-driven loading; make `consult` grinder-aware.
- **Phase 3: Parameterize new-coffee (SKILL.md + reference files)** — Replace the Sette fallback/defaults/vocabulary in `new-coffee/SKILL.md` and de-Sette its two loaded reference files so `/new-coffee` is behaviorally grinder-agnostic.

## Edge Cases

- **Grinder row missing / blank / whitespace / `None` (case-insensitive)** → no specific reference; grinder-relative step advice + unconfigured nudge (Req 4a).
- **`user-setup.md` unreadable** — file missing, the unconfigured template state (per CLAUDE.md's Unconfigured check), or a dangling symlink (it is a symlink into the private data repo) → the skills (including `consult`, newly exposed to this) degrade to the same fallback and never error (Req 4d).
- **Grinder field matches no keyword in the map** (e.g. the shipped `user-setup.example.md` value `Baratza Encore ESP (flat burr, stepped adjust)`) → fallback. This is the common forker case before they add a map row, and is treated as first-class, not exotic.
- **Mapped keyword matches but the reference file does not exist yet** (e.g. a `df64v`-containing field before 025 has created `DF64V.md` — though Req 1 gates against this) → fallback gracefully; never attempt to load a missing file.
- **User asks `consult` a grind question while on a non-Sette grinder** → routes to the ACTIVE grinder's reference (grinder-neutral keyword routing).
- **User types only the bare grinder proper-noun (e.g. "Sette") with no grind-context word** → no routing keyword matches and the question falls through to consult's `ESPRESSO_BREWING_BASICS.md` default (line 42). Accepted, low-severity: grinder questions normally include a grind-family word ("grind/finer/coarser/grinder"), the general file is not a wrong answer, and the user can rephrase. No grinder proper-noun is re-hardcoded as a keyword (that would reintroduce a Sette literal).
- **`consult` deep-reference tier requested but the active grinder has no `<GRINDER>_REFERENCE.md`** → `consult` answers from the quick reference only, respecting the cascade cap.
- **Forker adds a new grinder** → adds one keyword→file row to the CLAUDE.md contract and drops `knowledge/grinders/<GRINDER>.md` (optionally a `<GRINDER>_REFERENCE.md`). One-edit, no skill-logic change.

## Technical Constraints

- **Mirror the Puck Screen field parsing contract pattern** (CLAUDE.md + `feedback/SKILL.md:79`, `diagnose/SKILL.md:147`): the operative parsing rule is restated inline in each skill that reads the field and attributed to the CLAUDE.md SSOT clause; grinder domain content (notation, dial advice) is NOT copied into the skills — it is loaded from the active grinder reference as the single source of truth. The matching mechanism is a faithful mirror — fixed keyword set, case-insensitive substring, no normalization beyond case, no tie-break — not an extended algorithm. (An earlier draft proposed normalized-substring-against-filenames with longest-stem-wins; that was rejected as more than a prompt-only skill reliably executes and as overstating the Puck Screen precedent.)
- **Verification ceiling for prompt-only skills**: the grep acceptance criteria prove (a) the Sette literals are absent and (b) the resolution wiring is present (the skill points at `knowledge/grinders/`, names the contract, and carries the deferral/fallback instructions). They do NOT prove runtime resolution; that is verified by the Req 14 interactive dry-run. Greps + dry-run together are the verification strategy; neither alone is sufficient.
- **Forkability is one-edit, not zero-edit**: a forker adds a keyword→file map row and drops a reference file; the no-match fallback keeps the skills working (degraded but correct) until they do. The epic's "fork-and-plug-in" promise is satisfied by this one-edit path plus the always-working fallback.
- **`blocked-by: 025` is load-bearing and gated.** 027 consumes from 025: the `knowledge/grinders/<GRINDER>.md` references, the grinder-neutral notation that `feedback` defers to, and the re-keyed grinder-relative shared knowledge the fallback leans on. Overnight runs 025 first (blocked-by ordering); Req 1 additionally hard-gates on 025's named files existing, so a 025-incomplete state halts 027 rather than silently shipping. Residual risk to verify at implementation: 025 must leave the re-keyed shared knowledge usable standalone (no dangling "see your grinder reference" cross-link that dead-ends when no reference matches).
- **026 runs in parallel, not before.** At 027's build time the live Grinder field still reads `Baratza Sette 270 (conical burr, micro-adjust)`; the selector must resolve for whatever the field says. Only the Sette and fallback paths are testable against live config until 026 lands; the Sette path is concretely correct because `SETTE_270.md` already prescribes its notation.
- **Keep references one level deep** (Anthropic skills anti-pattern): the skill links directly to the resolved grinder reference, not chained through a shared-notation file.
- **`user-setup.md` is a symlink** into the private data repo; `feedback`'s grind-map write goes through the symlink and auto-commits to the private repo per the CLAUDE.md auto-commit policy — 027 must not alter that commit logic.
- **Protected paths**: `.claude/skills/**` are `noDeletePaths` (edit/write allowed; delete/rename blocked); changes route through the lifecycle. Preserve Core Rules verbatim — especially "Sour AND bitter = channeling → fix puck prep, NOT grind" — and do not disturb the existing Puck Screen parse blocks.
- **No project requirements doc constraints**: `cortex/requirements/project.md` is an unconfigured TODO template; governing constraints come from `CLAUDE.md`, the backlog tickets, and the damage-control hooks.
