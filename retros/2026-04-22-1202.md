# Session Retro: 2026-04-22 12:02

## Problems

**Problem**: Initial spec claimed `select`'s error shape was "matching the existing `manage_profile` error pattern" without verifying what that pattern actually was. Critical review's error-code reviewer inspected `errors.py` and `server.py` directly and found the existing `manage_profile` uses TWO shapes (bare validation branches + four-field `except GaggimateError`), and that `PROFILE_NOT_FOUND` + `INVALID_INPUT` are defined but never raised anywhere. **Consequence**: Full spec rewrite required to (a) drop the "matching existing pattern" framing, (b) explicitly call out the four-field shape as a deliberate divergence, (c) flag first-time raise sites as a `Changes to Existing Behavior` entry, and (d) add `PARSE_ERROR` to the possible-codes list. The original framing would have misled implementers into producing the bare shape and failing the acceptance test.

**Problem**: Initial spec's Edge Cases entry for "select succeeds but list refetch fails" returned `success: false` with `error_code: "API_ERROR"` — claiming in prose that this "doesn't mislead the caller" while the boolean contract said the opposite. Critical review's split-brain reviewer caught the contradiction. **Consequence**: Spec rewrite to invert the return shape — partial-success now returns `success: true` with `profiles_refetch_failed: true` + `selected_profile_id` + warning, omitting `profiles`. Had this shipped, agents would have retried or pivoted on `success: false` while the device was already on the new profile, silently breaking repo/device coherence.

**Problem**: Initial spec had no post-condition check that the target id was actually marked `selected: true` in the final list. Reviewer's race-window angle surfaced that `list_profiles()` at T+n is an observation, not a confirmation, and that firmware's unconditional UUID write means a deleted-between-load-and-select case lands as silent `success: true`. **Consequence**: Added R7 divergence detection to the spec, but the design flaw survived one orchestrator review round — P1–P6 passed despite this missing post-condition check.

**Problem**: Initial plan's Task 2 bundled 10+ distinct sub-operations (dispatch, input validation, name resolution, pre-validate with None→raise translation, select call, list refetch, divergence detection, three return branches, six error-code branches, docstring, unknown-action string) into one "15-minute" task whose verification was three greps for string presence. File count = 1 was treated as sufficient regardless of time. **Consequence**: Plan rewrite to split into Task 2 (happy path + pre-validate) and Task 3 (divergence + partial-success + docstring + unknown-action). A broken implementation would have passed Task 2's original greps and left the repo in a half-landed state when Task 4's tool-layer tests caught the regression.

**Problem**: Initial plan's Task 3 (WS method tests) had one test asserting only outgoing call args — did not test return pass-through or error propagation. The plan bothered to pin one layer but left the others unpinned, despite Task 1's explicit contract ("does not catch or re-wrap" the four raise paths). Task 4's tool-layer mocks would have silently masked a defensive `try/except GaggimateError: return None` regression. **Consequence**: Plan rewrite to expand Task 4 (renumbered) from 1 test to 5 covering pass-through + three error-code propagations. The asymmetry between 1 WS test and 10 tool-layer tests was the visible smell that orchestrator review did not catch.

**Problem**: Initial plan's Task 6 (interactive end-to-end verification) had no failure-recovery mechanism — prose in Context said "if observed, file a follow-up task" for firmware-race but no plan task existed for that, and the Veto Surface simultaneously allowed dropping Task 6 entirely. The Scope Boundaries ban on retries collided with the firmware-race mitigation hinted at in Task 6's own context. **Consequence**: Plan rewrite to add explicit failure-handling prose to (renumbered) Task 7 naming the three failure modes and their loop-back targets, reconcile Scope Boundaries ("race → new ticket, not Task 2 retry"), and remove Task 6 from the Veto Surface. The original plan would have left the lifecycle with no defined response when the only end-to-end gate failed.

**Problem**: Initial R7 (the `/new-coffee` skill update) had acceptance of just `grep -c 'action="select"' SKILL.md ≥ 1`. R7's reviewer demonstrated this matches comments, unreached examples, hard-coded literal ids, and out-of-order calls — a LLM-interpreted markdown file cannot be soundly gated by single-string greps. **Consequence**: Spec + plan rewrite to add four grep checks including a negative check (`grep -cE 'profile_id="[^"{]*"' == 0`) banning hardcoded string ids, and a create-failure short-circuit prose check. The user-visible acceptance was nearly the weakest-tested requirement in a ticket whose headline feature is the skill update.
