# Plan: post-upgrade-drift-investigation-mixed-era-retention-ordering-ble-precision

## Overview

The spike's only shipped deliverable is three dated sections appended to `research/gaggimate-1-8-0-upgrade/verification-notes.md`, each concluding with a three-valued verdict (`drift detected` | `no drift` | `unable to test`) plus a `Status:` marker. The work decomposes into five strands: (1) a baseline/final read-only invariant pair bracketing the spike window (Tasks 1 and 15, with Task 15's recovery path classifying intervening commits), (2) one live device call for sub-question (b) (Task 2), (3) seven parallel source-code audits (six named Req 4 sub-audits plus the parser decode-surface + BLE-path trace for sub-question c), (4) three section-compose tasks that weave the audit outputs into the verification-notes file, and (5) an independent re-fetch verification (Task 14) implementing spec Edge Case 7's two-fetch anti-hallucination pattern — every SHA-pinned blob URL cited in the three new sections is WebFetched again by a separate task agent and its adjacent quoted text is substring-validated against the fetched blob. Audits write intermediate markdown to `lifecycle/.../scratch/` (gitignored via a `scratch/.gitignore` containing `*`); compose tasks are the only writers to `verification-notes.md`. Task-level verifications are deliberately structural (shape, count, anchors); content-correctness is distributed between Task 14 (citation integrity) and the lifecycle review phase (everything else).

## Veto Surface

- **Tasks 9a/9b effort envelope (header-region byte enumeration, 431 bytes per tag).** Post-split, each is ~30–60 min if the agent applies collapse aggressively for long reserved/zero runs. Without collapse, 9a and 9b are each 431 manually-inspected rows and will still exceed the 5–15 min guideline. - **Device connectivity at execution time (Task 2).** Spec allows `unable to test` for (b) when the device is unreachable, but adversarial review specifically added the live-signal floor — weakening (b)'s verdict to source-only degrades evidence. If device is known-offline before the overnight run, the user may prefer to defer Task 2 and Task 4 until connectivity returns rather than landing an `unable to test` section prematurely.
- **BT-scale vendor-module is a pre-loaded trigger for (c) → `unable to test`.** Spec line 23 anticipates BT-scale as a plausible vendor-gated path (`"If any enumerated path cannot be fully traced from source (e.g., BT-scale BLE path is gated by a vendor-specific firmware module), the verdict is unable to test"`). Task 7's any-fail gate means one vendor-blocked module nullifies the full (c) audit even when all other evidence landed cleanly.
