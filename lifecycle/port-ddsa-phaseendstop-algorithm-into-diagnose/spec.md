# Specification: Port DDSA / PhaseEndStop algorithm into /diagnose

## Problem Statement

`/diagnose` currently emits a generic stop-target summary ("volumetric target reached", "phase duration reached") without telling the user which specific stop condition triggered each phase exit, and without estimating the scale-delay compensation the device's native analyzer computes. This leaves the agent unable to state "brew phase exited on volumetric at t+24.3s with estimated scale delay 1.2s" autonomously — the user has to open the native analyzer UI in a browser and read it visually. The firmware 1.8.0 native analyzer (`AnalyzerService.js`) already computes this classification and delay estimate; porting that algorithm to Python inside the MCP makes agent-autonomous shot diagnosis possible without a human-in-the-loop chart inspection. The user picked full-port over deep-link-only (DR-1) with explicit acceptance of the recurring firmware-upgrade maintenance tax.

10. **Tolerance-aware walker added to `shot_fixture_walker.py`**: `shot_fixture_walker.py` gains two optional parameters on `compare()` and `assert_equal()`: `float_tol: float = 0.0` (default preserves 016's exact equality) and `per_field_tol: Optional[dict[str, float]] = None` (keyed by field-path strings). When `float_tol > 0` and the leaf is `isinstance(expected, float) and isinstance(actual, float)`, comparison uses `math.isclose(expected, actual, abs_tol=float_tol, rel_tol=0.0)`. When `per_field_tol` maps a path to a float, that override wins; when the path maps to `None` or the special sentinel `EXACT`, the field uses strict `==` even under `float_tol > 0`. NaN-aware: `(math.isnan(expected) and math.isnan(actual))` compares equal. Integer-typed fields always compare with strict `==` regardless of `float_tol` (Python's `==` already handles this; the walker does not coerce). Existing tests in `test_shot_fixture_walker.py` continue to pass without modification (default behavior unchanged).

## Non-Requirements

- **No firmware startup-warning mDNS check.** The ticket AC does not require it; research surfaced it as a future enhancement. Out of scope for 018. Version-consistency drift is instead caught by R18 (static filename-vs-constant check); live device-firmware-vs-MCP-version drift monitoring remains manual via the runbook.
- **No CI integration.** The parity test runs locally only — `.github/workflows/` is absent from the repo and 018 does not introduce it. 013 epic's framing of "test passes" means local invocation passes.
- **No fixture recapture for 246/247/249 beyond adding `.profile.json` + `.reference-js.json` sidecars.** Existing `.slog` bytes and `.golden.json` files are not re-captured or re-serialized. The parity test adds new sidecars; it does not regenerate 016's contract.
- **No MVP-tier categorical-only fallback.** The port includes both `classify_phase_exits` and `estimate_auto_delay` in the initial release. Auto-delay is not deferred to a follow-up ticket.
- **No new MCP tool for classification.** DDSA results are surfaced by extending `analyze_shot` only — no separate `classify_phases` tool.
- **No skill output changes outside the specified three surfaces** (per-phase bullets under Phase Comparison, auto-delay bullet, trailing deep-link line). Diagnosis narrative, recommendations, and self-check `<claims>` block are unchanged.
- **No `power` pump-mode vocabulary expansion.** If fixture 249 contains a power-target phase, DDSA classifies its exit as `duration` (time-based, since power-target phases have no quantitative stop target in the JS). `models/profile.py` Pydantic `Literal["pressure", "flow"]` remains as-is; DDSA's `ProfileData` TypedDict reads raw JSON without Pydantic validation. Broader profile-model reconciliation is out of scope.
- **No tightening of parity tolerance below 1e-3 on float fields.** If implementation discovers genuine accumulation-order divergence, the per-field allowlist escape hatch is used — tolerance is not loosened globally, but specific fields may be exempted under R11's inline-comment-citation rule.
- **No runtime profile fetch retry logic.** If `manage_profile(action="get")` fails for any reason (device offline, UUID missing, renamed, WebSocket error), DDSA degrades immediately to `exit_reason_type="unknown"` + `unavailable_reason="profile_unavailable"` — no retries, no exponential backoff.
- **No deep-link suppression when offline.** The `Interactive chart:` line always renders. When `config.host` is unreachable or the shot is fixture-replayed, the URL may 404 — this is acceptable per the user's lightweight-copy choice. Runtime host-reachability gating is a separate enhancement.
- **No skill-output rendering test.** SKILL.md is prose-to-Claude, not executable code; Claude's adherence to the Response Format template is probabilistic. This matches every other skill in the project and is the established enforcement model. Rendering drift is caught by manual review during session use, not by automated test.
- **No synthetic fixture for scale-lost-permanently flag propagation.** User chose "Ship on 246/247/249, document gap" during Clarify. The four check sites + two fallback paths in the JS source are ported explicitly (reviewed in PR against the vendored JS); parity coverage is whatever the three committed fixtures happen to exercise. Gap is documented in `mcp/README.md`'s Known coverage gaps list.
- **No `cleanName` normalization in the Node harness.** `AnalyzerService.js` itself does only `.trim().toLowerCase()` on profile-phase names internally; the browser's outer caller applies `cleanName()` from `analyzerUtils.js` to the profile before passing it in, but the scope of that normalization beyond trim/lowercase is not investigated in 018. Committed fixture profile names (246/247/249) are assumed to be plain ASCII without punctuation that `cleanName` would strip. If a future fixture introduces a phase name that causes parity divergence, `cleanName` vendoring is tracked as a follow-up.

## Edge Cases

- **Profile fetch failure (`profile_unavailable`)**: `manage_profile(action="get")` may fail for multiple reasons — device offline, profile UUID no longer on device, profile renamed or re-IDed, WebSocket connection failure. All four collapse to `unavailable_reason="profile_unavailable"`. `analyze_shot` still emits the `analyzer_url` deep-link; skill renders "Exit reasons unavailable (profile unavailable)" + link.
- **Shot-history eviction mid-session (500KB purge)**: The deep-link to `/analyze/{id}` may 404 by the time the user clicks. Accepted per user's copy choice; URL renders plain without retention disclaimer.
- **Scale-lost-permanently flag propagation**: The sticky cumulative flag must be propagated across 4 check sites and 2 fallback paths (per JS source lines 407, 447, 545, 624, 691-692, 804). The port implements these sites explicitly (PR-reviewed against the vendored JS); the parity test covers whatever propagation the three committed fixtures happen to exercise. No synthetic fixture is added in 018 (gap documented in runbook).
- **Power-target phase exit (fixture 249 suspected)**: DDSA classifies as `duration` — no quantitative stop condition exists for power-target phases in the JS source. Implementation confirms behavior against reference-JS on fixture 249.
- **Downsampled `TransformedShot` input**: The port takes raw `ShotData`, not `TransformedShot`. Any caller passing a `TransformedShot` fails at type-check; no runtime fallback. `analyze_shot` uses the raw `shot_data` from `http_client.fetch_shot` directly for DDSA (before `transform_shot_for_ai` runs), not the downsampled transformed output.
- **`Math.round` banker's-rounding bucket flip at `.5` boundaries**: `js_round` replaces every bare `round()` in the module. `test_js_round.py` guards the semantic.
- **Non-numeric shot_id**: `shot_id.lstrip('0') or '0'` handles the "all zeros" and non-integer-prefix cases without raising. `analyze_shot` receives `shot_id: str` from the MCP caller and passes it to URL construction unchanged (after `lstrip`). R17's parametrized case covers this.
- **JSON float serialization round-trip drift**: Parity walker compares parsed doubles numerically with `math.isclose`, NOT JSON string equality — `JSON.stringify(0.1+0.2)` vs `json.dumps(0.3)` do not cause spurious failures. R17 extends this guarantee end-to-end through the MCP tool response.
- **Parity test adds fixture with no `.profile.json` or `.reference-js.json`**: Test fails that fixture explicitly with a `pytest.fail(...)` message naming the missing sidecar path AND linking to `mcp/README.md`'s "Adding a new fixture" section for remediation — does not skip silently.
- **Firmware version mismatch during capture**: If vendored `analyzer-service.*.js` content is updated without bumping `ANALYZER_JS_VERSION`, or vice versa, R18's consistency test catches the drift at `pytest` time — not reliant on PR-reviewer discipline.
- **Node version below 20.17**: ESM auto-reparse is required for `capture.js` to run without explicit `--input-type=module`. `package.json` pins `"type": "module"` so ESM is declared; `"engines": {"node": ">=20.17.0"}` is advisory but documented in runbook Prerequisites. Contributors on older Node see `SyntaxError: Unexpected token 'export'` — runbook directs them to upgrade.

## Technical Constraints

- Python 3.13+ (`mcp/pyproject.toml:9`). No new Python runtime dependencies. DDSA port is stdlib-only.
- Node.js harness requires `node >= 20.17.0` locally for fixture capture (ESM auto-reparse). Not a runtime dep of the MCP server; only needed for refresh. `package.json` declares `"type": "module"` and the `engines` pin.
