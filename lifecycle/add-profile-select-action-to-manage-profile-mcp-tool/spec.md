# Specification: Add `select` action to `manage_profile` MCP tool

## Problem Statement

The `manage_profile` MCP tool currently exposes `list`, `get`, `create`, `update`, and `delete`, but has no way to activate an uploaded profile as the device's current one. After a profile is created via MCP, the user must physically tap it on the Gaggimate screen to make it active — which breaks the end-to-end "coffee setup → shot" flow the agent drives. Concretely, `/new-coffee` can upload a profile but cannot tell the machine to use it, so the skill's happy path terminates one step short of pulling a shot. This ticket adds a `select` action and updates `/new-coffee` to call it, closing that gap for the principal caller (the agent) and for any ad-hoc user invocation.

## Requirements

All requirements are must-have.

1. **New `select` action on `manage_profile`**: Adding `action="select"` to `manage_profile` exposes a sixth action that activates a profile on the device.
   - Acceptance: `grep -c '"select"' mcp/src/gaggimate_mcp/server.py` ≥ 3 (dispatch branch, "Use:" error message, docstring enumeration); `mcp/src/gaggimate_mcp/server.py` contains an `elif action == "select":` branch inside the `manage_profile` function.

2. **Accept either `profile_id` or `profile_name`**: The action accepts one of two identifying arguments. Exactly one must be supplied; both present or neither present is an input error. When `profile_name` is supplied, the tool resolves it to an `id` by calling `req:profiles:list` and matching the `label` field (case-sensitive exact match).
   - Acceptance: unit test `test_select_resolves_profile_name_to_id` calls with `profile_name="Munyinya Light Bloom [AI]"`, asserts the ensuing `req:profiles:select` request carries the resolved `id`. Unit test `test_select_rejects_both_id_and_name` asserts an input-validation error when both are passed. Unit test `test_select_rejects_neither_id_nor_name` asserts an input-validation error when both are missing. `python -m pytest mcp/tests/test_manage_profile_select.py -k 'resolves_profile_name or rejects_both or rejects_neither' -v` exits 0.

3. **Pre-validate profile existence via `req:profiles:load`**: Before sending `req:profiles:select`, the tool calls `req:profiles:load` with the (possibly-resolved) id. **Implementation detail (not inferrable from the existing pattern)**: `WebSocketClient.load_profile` currently returns `None` for missing profiles rather than raising. The `select` action's validation layer must interpret a `None` return from `load_profile` as profile-not-found and raise `GaggimateError(ErrorCode.PROFILE_NOT_FOUND, ...)` itself; do not modify `load_profile`'s return semantics. If pre-validation raises (not-found, WS error, timeout), the tool returns the appropriate error without calling `req:profiles:select`.
   - Acceptance: unit test `test_select_prevalidates_with_load` mocks `load_profile` to return `None` for an unknown id and asserts that `_send_request` is NOT called with `request_type="req:profiles:select"` (mock `call_count` for that request type equals 0), and the response is `{"success": false, "action": "select", "error_code": "profile_not_found", ...}`. Separate test `test_select_prevalidate_ws_failure_propagates` mocks `load_profile` to raise `GaggimateError(WEBSOCKET_ERROR)` and asserts the response carries `error_code: "websocket_error"`. `python -m pytest mcp/tests/test_manage_profile_select.py -k 'prevalidates_with_load or prevalidate_ws_failure' -v` exits 0.

4. **WebSocket request shape `{tp: "req:profiles:select", rid, id}`**: A new public method `WebSocketClient.select_profile(profile_id: str) -> dict` in `mcp/src/gaggimate_mcp/api/websocket.py` uses `_send_request("req:profiles:select", request_id, id=profile_id)` — mirroring the existing `save_profile` / `delete_profile` shape. It waits for `res:profiles:select` within the existing 5 s timeout and raises `GaggimateError` on `error` field or timeout, matching the existing `_send_request` pattern.
   - Acceptance: unit test `test_select_profile_sends_correct_request` mocks `_send_request` and asserts it is called with `(request_type="req:profiles:select", request_id=<any>, id=<profile_id>)`. `python -m pytest mcp/tests/test_api_websocket.py -k 'test_select_profile_sends_correct_request' -v` exits 0.

5. **Return shape on happy path: full updated profile list with verified target**: On the full happy path — pre-validate succeeds, `req:profiles:select` returns without error, `list_profiles()` refetch succeeds, AND the refetch shows the target id with `selected: true` — the tool returns `{"success": true, "action": "select", "profiles": [...], "count": N}` (same shape as `action="list"`).
   - Acceptance: unit test `test_select_returns_full_updated_list` mocks the selection and a subsequent `list_profiles` return where the target profile shows `selected: true` and all others `selected: false`; asserts the response JSON has top-level `profiles` array, `count` equal to array length, `success: true`, `action: "select"`. `python -m pytest mcp/tests/test_manage_profile_select.py -k 'returns_full_updated_list' -v` exits 0.

6. **Return shape on partial success (select landed, verification unavailable)**: When `req:profiles:select` returned without error but the subsequent `list_profiles()` refetch raises (WS error, timeout, parse error), the tool returns `{"success": true, "action": "select", "selected_profile_id": "<id>", "profiles_refetch_failed": true, "warning": "Profile selected on device; list verification unavailable: <refetch error>. Run manage_profile(action='list') to refresh."}` — the `profiles` field is omitted entirely on this path. Rationale: the select WS op succeeded, so the device DID change state; returning `success: false` would mislead the agent into retry/pivot while the device is already on the new profile. Omitting `profiles` (rather than sending a possibly-stale one) signals "verification unavailable" to the caller.
   - Acceptance: unit test `test_select_partial_success_list_fails` mocks `_send_request` to succeed for `req:profiles:select` and raise `GaggimateError(API_ERROR)` for the subsequent `list_profiles`; asserts `success: true`, `selected_profile_id` equals the target id, `profiles_refetch_failed: true`, no top-level `profiles` key present. `python -m pytest mcp/tests/test_manage_profile_select.py -k 'partial_success_list_fails' -v` exits 0.

7. **Post-condition check — selection divergence**: After a successful `list_profiles()` refetch, the tool inspects the returned list for the target id. If the target id is NOT marked `selected: true` (another writer — touchscreen tap, concurrent MCP call, or a firmware edge that silently dropped a dangling-UUID select — has changed the selection), the tool returns `{"success": false, "action": "select", "error_code": "api_error", "error": "Selection divergence: profile '<target_id>' is not marked selected in device list after select call. Device may show '<actually_selected_id_or_none>' instead. Another writer may have changed selection between operations.", "suggestion": "Retry manage_profile(action='select', profile_id='<target_id>'), or call manage_profile(action='list') to inspect current state.", "profiles": [...]}` — the full returned list is included so the caller can see the actual device state.
   - Acceptance: unit test `test_select_detects_selection_divergence` mocks the select to succeed and the subsequent `list_profiles` to return a list where a DIFFERENT profile shows `selected: true`; asserts `success: false`, `error_code: "api_error"`, `error` contains the substring "Selection divergence", and `profiles` is present. `python -m pytest mcp/tests/test_manage_profile_select.py -k 'detects_selection_divergence' -v` exits 0.

8. **Standard four-field error response shape, consistently**: On every failure path, the tool returns `{"success": false, "action": "select", "error": "<msg>", "error_code": "<code>", "suggestion": "<hint>"}` — always all five keys. Possible `error_code` values: `profile_not_found` (pre-validation fails to find the id/name), `websocket_error` (WS unreachable), `timeout` (WS timeout), `parse_error` (device returned malformed JSON — `_send_request` can raise this per `websocket.py` behavior), `api_error` (post-select verification divergence or list-response malformed), `invalid_input` (both/neither of id/name; label-match ambiguity; empty string input). **Explicit note**: this four-field-always shape is STRICTER than the existing `manage_profile` action's pattern. `get`/`update`/`delete`'s validation branches currently emit bare `{"success": false, "error": "<msg>"}` without `error_code` or `suggestion`. `select` breaks parity deliberately — implementers must NOT copy from `get`/`update`/`delete`'s bare-shape branches; use the four-field shape from server.py's `except GaggimateError` handler (currently lines ~449-453) as the template. `ErrorCode.PROFILE_NOT_FOUND` and `ErrorCode.INVALID_INPUT` exist in `mcp/src/gaggimate_mcp/errors.py` but have no current raise sites in the codebase; `select` is their first raise site. Implementers construct `GaggimateError(ErrorCode.PROFILE_NOT_FOUND, "...")` explicitly.
   - Acceptance: unit test `test_select_error_shape_all_codes` parametrizes over the six error codes and asserts each response has all five fields present (`success`, `action`, `error`, `error_code`, `suggestion`) and `error_code` matches the expected string. `python -m pytest mcp/tests/test_manage_profile_select.py -k 'test_select_error_shape_all_codes' -v` exits 0.

9. **`/new-coffee` skill calls select after create, with id capture and create-failure short-circuit**: `.claude/skills/new-coffee/SKILL.md` is updated so the upload step: (a) calls `manage_profile(action="create", ...)`; (b) captures the return into a named variable (convention: `created_profile`); (c) checks `created_profile["success"]` — if `false`, surfaces the error to the user and does NOT call select; (d) otherwise extracts the id via `created_profile["profile"]["id"]` (this is the shape returned by the existing `create` action — confirmed by reading `server.py`'s create branch during implement phase) and calls `manage_profile(action="select", profile_id=<extracted_id>)`; (e) checks the select response and surfaces any `success: false` error rather than claiming activation.
   - Acceptance (static, all runnable without device):
     - `grep -c 'manage_profile(action="create"' .claude/skills/new-coffee/SKILL.md` ≥ 1
     - `grep -c 'manage_profile(action="select"' .claude/skills/new-coffee/SKILL.md` ≥ 1
     - `grep -cE 'profile_id="[^"{]*"' .claude/skills/new-coffee/SKILL.md` == 0 (no hardcoded-string `profile_id` — catches `profile_id="abc-123"` but allows `profile_id="{created_profile[profile][id]}"` style templates and `profile_id=created_profile['profile']['id']` variable references)
     - The skill's upload section contains prose explicitly describing create-failure short-circuit — grep for at least one of the strings `success": false` or `success: false` or `create failed` or `If create returns` in the same section as the `manage_profile(action="create"` call.
   - Acceptance (interactive/session-dependent verification in the implement phase): one end-to-end `/new-coffee` run on the real device with an already-researched coffee. After the run completes, `manage_profile(action="list")` output shows **exactly one** profile with `selected: true`, AND that profile's `id` matches the id of the profile just created, AND every other profile in the list shows `selected: false`. Interactive/session-dependent rationale: exercises the MCP↔firmware↔skill loop end-to-end, which the unit tests (all mocked) cannot.

10. **Action list and tool docstring updated**: `server.py`'s "Unknown action" error message on the existing line ~443 (currently `"Use: list, get, create, update, delete"`) is updated to include `select` — the literal string must become exactly `"Use: list, get, create, update, delete, select"`. The `manage_profile` tool docstring enumerates `select` among the available actions with a one-line description. If `mcp/README.md` (or any MCP-documenting file discovered during implement) contains an action table for `manage_profile`, `select` is added there; if no such table exists, no new documentation file is created.
   - Acceptance: `grep -F 'list, get, create, update, delete, select' mcp/src/gaggimate_mcp/server.py` exits 0 (literal string match); unit test `test_manage_profile_unknown_action_lists_select` calls the tool with an unknown action and asserts the returned error string includes `select` in the enumeration.

## Non-Requirements

- **No repo-side mirror of the active-profile pointer.** The device is the authority (queryable via `list`). The `select` action does not write to `user-setup.md`, `.data-repo-path`'s private repo, or any file under `coffees/`. Agent-side durable pointer is a potential follow-up ticket, not part of this work.
- **No HTTP transport addition to profile operations.** Firmware exposes no HTTP profile endpoints; `mcp/src/gaggimate_mcp/api/http.py` is not touched.
- **No firmware-side changes.** This ticket consumes a protocol that already exists on `master` (`jniebuhr/gaggimate`); no firmware PR or version gate.
- **No `req:profiles:save` with `selected: true` path.** Save does not drive activation in the firmware; only `req:profiles:select` does. The spec does not include a fallback via save.
- **No paired deselect of the previously-active profile.** Firmware's `setSelectedProfile(uuid)` is a single-value setter; the MCP does not explicitly deselect anything.
- **No active-shot guard.** If the user triggers `select` while a shot is in progress, the tool forwards the request to the firmware and returns whatever the firmware returns. Behavior in that window is firmware's concern, not the MCP's.
- **No change to the `selected` field on `req:profiles:save` payloads.** `create_or_update_profile` continues to write `"selected": false` as today; that is separate plumbing from activation and is out of scope.
- **No new tool.** `select` is an action on the existing `manage_profile` tool, not a standalone MCP tool.
- **No modification to `WebSocketClient.load_profile`'s return semantics.** It continues to return `None` for missing profiles. The select action's validation layer interprets `None` as not-found and raises `GaggimateError(PROFILE_NOT_FOUND)` itself, rather than refactoring `load_profile` to raise. Rationale: avoid rippling the contract change into all other callers of `load_profile`.
- **No retry loop in the MCP for selection divergence.** R7's divergence case returns a distinct error to the caller; it does not silently re-attempt the select. Retry is a caller-level policy decision.
- **No atomicity guarantee across the 4-round-trip sequence.** The tool explicitly does not guarantee that no other writer has mutated device state during `list→load→select→list`. R6 (partial success) and R7 (divergence check) are the spec's best-effort responses to this reality; stronger atomicity would require device-side locking (out of scope).

## Edge Cases

- **`profile_id` refers to a deleted or unknown profile**: Pre-validation via `load_profile` returns `None`; select-action validation raises `GaggimateError(PROFILE_NOT_FOUND)`; tool returns `{success: false, error_code: "profile_not_found", ...}`. `req:profiles:select` is never sent.
- **`profile_name` matches zero profiles**: After `list`, no label matches; tool returns `{success: false, error_code: "profile_not_found", error: "No profile with label '<name>'", ...}`.
- **`profile_name` matches multiple profiles (label collision)**: Tool returns `{success: false, error_code: "invalid_input", error: "Multiple profiles match label '<name>': [<id1>, <id2>, ...]. Use profile_id to disambiguate.", ...}`. Does not silently pick one.
- **Both `profile_id` and `profile_name` supplied**: `{success: false, error_code: "invalid_input", error: "Pass exactly one of profile_id or profile_name, not both.", ...}`.
- **Neither `profile_id` nor `profile_name` supplied**: `{success: false, error_code: "invalid_input", error: "One of profile_id or profile_name is required.", ...}`.
- **Empty-string `profile_id` or `profile_name`**: Treated as missing for that slot. Raises `invalid_input`.
- **WebSocket unreachable or timeout during the initial list (name-resolution path)**: Tool returns `{success: false, error_code: "websocket_error"|"timeout", ...}`. Never reaches pre-validate.
- **WebSocket unreachable or timeout during pre-validate `load`**: Surface the underlying `websocket_error` or `timeout`; do not attempt `select`.
- **WebSocket unreachable or timeout during `select`**: Surface `websocket_error` or `timeout`. Because `setSelectedProfile` is a single firmware call, there is no partial-state window on the MCP side to clean up.
- **Select WS op returned `error` field set in `res:profiles:select`**: `_send_request` raises `GaggimateError(API_ERROR, <msg>)`; tool returns `{success: false, error_code: "api_error", ...}`.
- **Device returns malformed JSON on any step**: `_send_request` raises `GaggimateError(PARSE_ERROR)`; tool surfaces `error_code: "parse_error"`.
- **`select` WS op succeeds, subsequent `list_profiles` fails (split-brain)**: Per R6 — tool returns `success: true` with `profiles_refetch_failed: true` + `warning` + `selected_profile_id`, omits `profiles`. Device state did change; caller should not retry.
- **`select` WS op succeeds, `list_profiles` succeeds, but target id is NOT `selected: true` in the returned list (selection divergence / TOCTOU)**: Per R7 — tool returns `success: false, error_code: "api_error"` with a Selection-divergence error message, includes the full returned `profiles` list so the caller can see actual state. Possible causes: concurrent touchscreen tap, concurrent MCP `select` call, or firmware silently dropped a dangling-UUID select (e.g., profile was deleted via another channel between our `load` pass and our `select`).
- **Select during an active shot**: Forwarded to firmware. MCP does not guard. Documented in the tool docstring as user responsibility.
- **Select-then-select the same profile**: Idempotent at firmware level (same UUID re-pinned). Pre-validate → select → list all succeed → divergence check passes. Returns success.
- **Concurrent MCP `select` calls from two sessions**: Each call's 4 round-trips can interleave arbitrarily. The post-condition divergence check (R7) means whichever call completes its final `list` seeing a DIFFERENT profile selected returns divergence — an honest error rather than a silent lie. At least one call returns success with the correct target; the other may return divergence or success depending on interleaving. Not atomic, but at least not silently wrong.

## Changes to Existing Behavior

- **ADDED: `manage_profile(action="select", profile_id=..., profile_name=...)`** — new sixth action on the existing tool; returns full updated profile list on success, or partial-success / divergence / error shape on the paths enumerated in R5–R8.
- **MODIFIED: `manage_profile` tool's "Unknown action" error message** — the listing of valid actions now ends with `, select` (exact string `"Use: list, get, create, update, delete, select"`).
- **MODIFIED: `manage_profile` tool docstring** — enumerates `select` with a one-line description among the other actions; the rest of the docstring is unchanged.
- **ADDED: `WebSocketClient.select_profile(profile_id: str) -> dict`** in `mcp/src/gaggimate_mcp/api/websocket.py` — new public method next to `save_profile` / `delete_profile`. The module docstring's list of request types gains `req:profiles:select`.
- **ADDED: first-time raise sites for `ErrorCode.PROFILE_NOT_FOUND` and `ErrorCode.INVALID_INPUT`** — both enum values exist in `errors.py` but were never raised in the current codebase. The select action is the first caller to `raise GaggimateError(ErrorCode.PROFILE_NOT_FOUND, ...)` and `raise GaggimateError(ErrorCode.INVALID_INPUT, ...)`. This does not modify existing callers; they continue to use their current bare-error shape.
- **ADDED: `/new-coffee` skill upload step now calls `manage_profile(action="select", profile_id=created_profile["profile"]["id"])`** after `manage_profile(action="create", ...)`, with create-failure short-circuit prose. The rest of the skill (research, grind map, etc.) is untouched.

## Technical Constraints

- **Firmware protocol (ground-truth)**: `req:profiles:select` with `{tp, rid, id}` is handled in `src/display/plugins/WebUIPlugin.cpp` of `jniebuhr/gaggimate`. It invokes `ProfileManager::selectProfile(uuid)` → `_settings.setSelectedProfile(uuid)`, a single-value setter. Firmware enforces single-select; no paired deselect required.
- **Response body shape**: Per AsyncAPI spec in `docs/websocket-api.yaml` of the firmware repo, `res:profiles:select` carries only `{tp, rid, error?}` — **no profile payload**. This is why the tool must re-fetch via `list_profiles()` to produce a useful return; it cannot pass through `res:profiles:select`. It is also why R6's partial-success path exists: the re-fetch is a separate WS round-trip that can independently fail.
- **Firmware does not validate UUID existence before selection** — `setSelectedProfile` writes unconditionally (confirmed via web research of the firmware source). Pre-validation via `req:profiles:load` (R3) prevents the static "id known to be missing" case, but cannot prevent TOCTOU between `load` and `select`. R7's post-condition divergence check is the catch for that window.
- **`WebSocketClient.load_profile` returns `None` for missing profiles, does not raise** (observed in `mcp/src/gaggimate_mcp/api/websocket.py:155-182`). The select action's validation layer is responsible for translating `None` into `GaggimateError(PROFILE_NOT_FOUND)` — see R3 implementation detail.
- **`create_or_update_profile` unconditionally writes `"selected": false` on save.** The `select` action therefore cannot rely on `save` to activate; activation and content-write are separate concerns. (Pre-existing behavior; unchanged by this ticket.)
- **`_send_request` contract**: existing WS helper opens a connection per request, sends the JSON payload, waits for the correlated `res:*` by `rid` with a 5 s timeout, and maps failures to `GaggimateError` with codes `WEBSOCKET_ERROR`, `TIMEOUT`, `PARSE_ERROR`, or `API_ERROR`. `select_profile` must match this contract exactly.
- **Existing `manage_profile` uses TWO error shapes** (observed in `mcp/src/gaggimate_mcp/server.py`): validation branches in `get`/`update`/`delete` emit bare `{"success": false, "error": "<msg>"}` with no `error_code`; only the outer `except GaggimateError` handler (~lines 449-453) emits the four-field shape. The select action uses the four-field shape on every failure path (R8) — this is a deliberate divergence for cleaner error taxonomy in the new code. Do not propagate the divergence back into existing actions in this ticket.
- **Error code enum values used**: `ErrorCode.PROFILE_NOT_FOUND`, `ErrorCode.INVALID_INPUT`, `ErrorCode.WEBSOCKET_ERROR`, `ErrorCode.TIMEOUT`, `ErrorCode.PARSE_ERROR`, `ErrorCode.API_ERROR` — all exist in `mcp/src/gaggimate_mcp/errors.py`. No new enum values introduced. `ErrorCode.DEVICE_UNREACHABLE` (used in the HTTP path) is NOT used here because the WS path's mapping in `_send_request` surfaces WS-connection issues as `WEBSOCKET_ERROR` — matching this is correct, not a taxonomy bug.
- **Repo-first rule applicability**: CLAUDE.md's "Repo first, device second" governs profile *content* writes (create/update). `select` is ephemeral device state with no repo counterpart, so the rule is orthogonal and no auto-commit is triggered.
- **Firmware version**: handler is present on master; the project runs firmware 1.8.0. No version-gate needed.

## Open Decisions

None. The spec resolves return shape (R5 happy path, R6 partial success, R7 divergence), error taxonomy (R8 four-field shape always, six codes listed, first-time raise sites acknowledged), and skill-layer gating (R9 with multiple static grep checks + strengthened interactive check).
