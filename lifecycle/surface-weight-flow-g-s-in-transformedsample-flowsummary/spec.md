# Specification: Surface `weight_flow_g_s` in TransformedSample + FlowSummary

> **Epic context**: This ticket is scoped from the broader firmware 1.8.0 adaptation epic. See [`research/gaggimate-1-8-0-upgrade/research.md`](../../research/gaggimate-1-8-0-upgrade/research.md), Decision Record DR-4. Research for this ticket is in [`research.md`](research.md).

## Problem Statement

The `analyze_shot` MCP tool does not expose per-sample weight flow (grams/second) today, even though the firmware has always logged it (`vf` field, bit 8 of the sample mask) and the parser already decodes it. Consumers that could benefit — `/diagnose` for channeling correlation, future `/feedback` adjustments, plotting tooling — cannot see the signal. Ticket 015 closes this gap by surfacing one per-sample field and three hygiene-filtered aggregates through the existing transformer pipeline, with fixture-backed regression coverage from 016's harness. The authoritative diagnostic-interpretation layer (a pump-flow vs weight-flow divergence call-out in `/diagnose`) is explicitly out of scope for 015; it is separately owned by ticket 018's DDSA port or a future successor ticket.

## Unified Hygiene Rule

R2, R3, and R4 all apply the same base validity predicate when deriving aggregates from per-sample `vf`:

```
valid(sample) ≡ ('vf' in sample)
            AND (abs(sample['vf']) < 20.0)     # drop firmware int16 clamp sentinels
            AND (sample.get('pf', 0.0) > 0.0)  # require pump flow — water must be moving
```

Rationale for the three filters:
- **Presence guard** (`'vf' in sample`) distinguishes "field absent" (older firmware, smaller `fields_mask`) from "weight flow is zero." The parser emits `vf` only when bit 8 is set.
- **Sentinel drop** (`abs(vf) < 20.0`). Firmware parses `vf` as a signed int16 scaled by 100, clamping at ±20.00 g/s. Values at the clamp are indistinguishable from legitimate boundary data and must be treated as unknown. The strict-less-than is a deliberate choice: rare ristretto shots that genuinely peak at 20+ g/s are undetectable post-hoc, so the conservative reading drops the edge. This is a known acknowledged limitation (not a bug).
- **Pump-flow cross-validation** (`pf > 0`). A scale-tare event or spurious weight spike BEFORE the pump is running is not real extraction. Fixture 247 contains exactly this failure mode: at t=0.75s the raw data is `vf=6.9, v=6.9, pf=0.0` — a tare event where weight and weight-flow both register but no water is moving. Requiring `pf > 0` rejects all such pre-pump and between-pump tare artifacts.

The three aggregates layer additional filters on top of `valid()`:
- **R2 (peak)**: also requires `vf > 0.0` (zero is not a "peak").
- **R3 (avg, brew-phase)**: further restricts to brew-phase samples (`cp ≥ 50% of peak cp`, via `_get_brew_phase_samples`). Does NOT additionally filter out zero or negative `vf` — during brew, a negative `vf` indicates scale drift-correction and is part of the honest signal for that shot. If fewer than 3 `valid` brew-phase samples exist, return `None` (mirrors the `ComplianceMetrics` degenerate-case pattern).
- **R4 (time_to_first_nonzero)**: further requires `vf > 0.3` (BT scale noise floor) AND `v > 0.0` (cup weight has registered). The combination of `pf > 0`, `vf > 0.3`, and `v > 0` triple-gates against tare events, pre-pump noise, and bloom-phase gravity drips.

## Requirements

1. **`TransformedSample.weight_flow_g_s` per-sample field.** Add a `weight_flow_g_s: float` field to the `TransformedSample` TypedDict in `mcp/src/gaggimate_mcp/transformers/shot.py`. Populate it in `select_representative_samples` via `round(sample.get('vf', 0.0) * 10) / 10`, mirroring the existing `flow_ml_s` derivation. Absent `vf` → `0.0` per existing convention. **AC**: (a) `grep -c 'weight_flow_g_s: float' mcp/src/gaggimate_mcp/transformers/shot.py` returns ≥ 1; (b) `grep -c 'weight_flow_g_s=round' mcp/src/gaggimate_mcp/transformers/shot.py` returns ≥ 1; (c) for every regenerated fixture golden, `jq -e '[.phases[].samples[] | has("weight_flow_g_s")] | all' <golden>` exits 0.

2. **`FlowSummary.peak_weight_flow_g_s`** aggregate. Add `peak_weight_flow_g_s: Optional[float]` to `FlowSummary`. Computation: over `clean_samples` (same scope as `peak_flow_ml_s`), collect `[s['vf'] for s in clean_samples if valid(s) and s['vf'] > 0.0]` where `valid` is the Unified Hygiene Rule above. Return `round(max(values) * 10) / 10` or `None` if the list is empty. **AC**: (a) `grep -cE 'peak_weight_flow_g_s: Optional\[float\]' mcp/src/gaggimate_mcp/transformers/shot.py` returns 1; (b) for every regenerated golden, `jq -e '.summary.flow.peak_weight_flow_g_s == null or (.summary.flow.peak_weight_flow_g_s > 0 and .summary.flow.peak_weight_flow_g_s < 20.0)' <golden>` exits 0 (sentinel rejection invariant: peak is either null or strictly inside the (0, 20) open interval); (c) for fixture 247 specifically, `jq -e '.summary.flow.peak_weight_flow_g_s == null or .summary.flow.peak_weight_flow_g_s <= 10.0' mcp/tests/fixtures/shots/247.golden.json` exits 0 (fixture 247 contains no legitimate peak `vf` above ~10 g/s once the tare spike at t=0.75s is rejected by the `pf > 0` guard; value may be null if no sample both has `pf > 0` and positive non-sentinel `vf`).

3. **`FlowSummary.avg_weight_flow_g_s`** aggregate (brew-phase only). Add `avg_weight_flow_g_s: Optional[float]` to `FlowSummary`. ## Edge Cases

- **Shot with no `vf` samples at all** (older firmware or truncated `fields_mask`): all aggregates → `null`; per-sample `weight_flow_g_s` = 0.0 for every sample.
- **Shot with only clamp-sentinel `vf` values (all ±20.0)**: all filters drop every sample → all aggregates `null`.
- **Shot with mixed negative and positive `vf` during brew**: `avg_weight_flow_g_s` includes the negatives (honest signal of scale drift during brew). `peak_weight_flow_g_s` excludes zeros and negatives. `time_to_first_nonzero_weight_flow_s` requires the triple-gate (`pf > 0`, `vf > 0.3`, `v > 0`).
- **Bloom-phase gravity-feed event** (pump off, gravity push water into puck): `pf = 0` during bloom, so all three aggregates reject these samples via the unified hygiene rule. `time_to_first_nonzero_weight_flow_s` will not fire on bloom drips.
- **Pre-shot scale tare spike**: fixture 247's canonical example at t=0.75s has `vf=6.9, v=6.9, pf=0.0`. The `pf > 0` requirement rejects it in all three aggregates. At t=1.0s, `vf=20.0` (clamp sentinel) is also dropped by `abs(vf) < 20.0`.
- **Shot ended before real flow began** (scale malfunction or shot aborted): aggregates likely `null`; `time_to_first_nonzero_weight_flow_s` = `null`.
- **Shot with `v` permanently 0 but `vf` positive and pump flowing**: scale-failure mode. `time_to_first_nonzero_weight_flow_s` = `null` via cup-weight cross-validation. `peak_weight_flow_g_s` and `avg_weight_flow_g_s` may still compute from `vf` (unified hygiene doesn't require `v > 0` for peak/avg).
- **Ristretto shot legitimately at or above 20 g/s**: the sentinel filter drops the peak, so `peak_weight_flow_g_s` may be `null` or lower than reality. Acknowledged limitation: clamp values cannot be disambiguated from real boundary signals post-hoc.
- **Python version upgrade changes round() semantics**: R7's inline comment documents the dependency. Regression fails on upgrade; remediation is to re-verify hygiene logic and regenerate goldens. Migration concern, not runtime.
- **021 BLE-precision drift (active sibling investigation)**: ticket 021 is investigating whether the 1.8.0 firmware's `std::to_string` (6-digit default) → `atof` round-trip introduces LSB drift in BLE-parsed floats including `vf`. If 021 finds systematic drift, 015's committed goldens may become incorrect for re-captured shots. Rounded aggregates (1 d.p.) should be resilient to sub-0.01 drift in most cases, but R4's raw-value threshold `vf > 0.3` could flip for samples very near the boundary. Mitigation if 021 surfaces drift: regenerate 015's goldens and tighten R4's threshold (e.g., 0.5 g/s) as a follow-up. No gate on 021 in 015.

## Technical Constraints

- **TypedDict-based schema.** All four new fields are additive TypedDict entries. No Pydantic migration, no runtime validation layer, no versioning.
- **Byte-stable golden JSON.** 016 R3 convention: `json.dumps(sort_keys=True, indent=2)` + trailing newline, UTF-8. New keys interleave alphabetically with existing ones. In the current schema: `peak_weight_flow_g_s`, `avg_weight_flow_g_s`, `time_to_first_nonzero_weight_flow_s` sort among the existing `FlowSummary` keys (before `total_volume_ml`, after `time_to_first_drip_s` / `time_to_first_weight_s`); `weight_flow_g_s` sorts before the existing `weight_g` in per-sample dicts. Net effect: pure line insertions on the current schema. R6(c) validates value-preservation via jq-normalized comparison, which is robust to sort-order churn unlike a raw line-level diff.
- **Exact-equality fixture assertion.** 016 R4 convention: no float tolerance. All new aggregates are pre-rounded to 1 decimal place via `round(x * 10) / 10`.
- **Python 3 `round()` banker's rounding (round-half-to-even).** Pinned via R7's inline comment + golden byte-stability. Python-version upgrade remediation is to re-verify hygiene and regenerate goldens.
- **Fixture walker location.** The deep-equality walker lives at `mcp/tests/shot_fixture_walker.py` (tests helper module), not under `src/gaggimate_mcp/tools/`.
- **`refresh_fixtures.py` CLI.** Located at `mcp/src/gaggimate_mcp/tools/refresh_fixtures.py`. Supports two modes: `--fetch <shot_id>` (captures `.slog` from device, then regenerates golden) and default mode (regenerates golden from committed `.slog`). Device-query IDs are zero-padded to 6 digits internally (shot_id="247" → device request uses "000247"); fixture filenames use the unpadded shot_id as supplied (`247.slog`, `247.golden.json`).
- **Pathological `vf` data in existing fixtures.** Fixture 247 carries 37 negative `vf` samples including 8 at the `-20.0` clamp floor, plus pre-pump tare spikes at t=0.75s (`vf=6.9, v=6.9, pf=0.0`) and t=1.0s (`vf=20.0, v=27.7, pf=0.0`). Fixture 249 carries 32 negative `vf` samples plus an early tare spike. Hygiene rules (R2/R3/R4) must correctly reject these — R2(c) and R4(c) assert the rejection explicitly on fixture 247.
- **Brew-phase filter uses `cp ≥ 50% peak cp`.** R3 reuses `_get_brew_phase_samples`, matching the `compute_compliance_metrics` convention. Do not introduce a new brew-phase definition.
- **`None` vs `0.0` for degenerate aggregates.** Mirror the `ComplianceMetrics` precedent: emit `None` (JSON `null`) when insufficient qualifying samples exist. Never silently emit `0.0` — that hides data-quality issues.
- **Unified hygiene filter rationale.** R2/R3/R4 share the `valid(sample)` base predicate (presence + sentinel + `pf > 0`) rather than three independent filter chains. The cross-validation is principled: the per-aggregate extensions (`vf > 0` for peak; brew-phase + n≥3 for avg; `vf > 0.3` + `v > 0` for first-nonzero) are each justifiable in isolation on top of the shared base.
- **Token-budget impact.** ~1.2 KB added per fixture (~9% bloat). Acceptable; independent of 001.
